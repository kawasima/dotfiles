# Data Modeling Skill

イミュータブルデータモデルの原則に従ってデータモデルを設計するスキル。
UPDATEを最小化し、INSERT ONLYに近い設計を目指す。

## Instructions

ユーザーから業務要件を受け取り、以下の5ステップに沿ってデータモデルを設計・出力する。

### Step 1: エンティティ抽出

5W1Hフレームワークでエンティティを洗い出す:

| 分類 | 問い | 例 |
|------|------|-----|
| Who | 誰が | 従業員、患者、顧客 |
| What | 何を | 製品、サービス、コース |
| When | いつ | 時間、日付、月、年度 |
| Where | どこで | 送付先、URL、IPアドレス |
| Why | なぜ | 注文、返品、入金 |
| How | どうやって | 請求書、契約書、注文書 |

命名規則:
- 無駄な接尾辞を避ける(「情報」「データ」「処理」「物」「マスタ」「記録」は付けない)
- 発音可能で視認性の高い短縮名を使う

### Step 2: リソースとイベントの分類

日時属性の有無で分類する:

- **リソース(R)**: 日時属性を持たない。「〜する」で表現できない(例: 会員、商品、部門)。5W1HのWho, What, When, Where
- **イベント(E)**: 日時属性を持つ。「〜する」で表現できる(例: 注文、支払い、配属)。5W1HのWhy, How

「マスタ/トランザクション」分類は使わない。曖昧で不毛な議論を招く。

### Step 3: イベントエンティティは1つの日時属性のみ

最重要ルール: **1つのイベントエンティティは1つの日時属性のみ持つ**

複数の日時属性を持つイベントは分割する:

```
NG:
  注文(E): 注文ID, 注文日時, 注文確認日, 配送日時, 配送完了日時
  → 各日時のUPDATEルールが異なり複雑化

OK:
  注文(E): 注文ID, 注文日時
  注文確認(E): 注文確認ID, 注文ID(FK), 注文確認日
  配送(E): 配送ID, 注文ID(FK), 配送日時
  配送完了(E): 配送完了ID, 配送ID(FK), 配送完了日時
  → INSERT ONLYでUPDATEなし
```

#### ロングタームイベントパターン

開始と終了を持つイベントはスーパータイプ化する:

```
入会(ロングタームイベント): 入会ID, ステータス
  入会アクティビティ(スーパータイプ): アクティビティID, 入会ID(FK), 日時
    ├─ 入会申し込み(E): 申し込み内容
    ├─ 審査(E): 審査結果
    └─ 会員証発行(E): 会員証番号

処理:
  1. 入会申し込み → 入会, 入会アクティビティ, 入会申し込み にINSERT
  2. 審査 → 入会アクティビティ, 審査 にINSERT。入会.ステータスをUPDATE
  3. 発行 → 入会アクティビティ, 会員証発行 にINSERT。入会.ステータスをUPDATE
```

ロングタームイベントのステータスUPDATEのみが許容されるUPDATE。

### Step 4: リソースの隠れたイベントを抽出する

リソースにUPDATE日時を持たせたい衝動は、未抽出のイベントが存在するサイン。

```
NG:
  会員(R): 会員ID, 氏名, メール, 更新日時
  → 何がいつ変わったか不明

OK:
  会員(R): 会員ID, 氏名, メール
  会員情報変更(E): 変更ID, 会員ID(FK), 変更日時, 変更内容
  強制退会(E): 退会ID, 会員ID(FK), 退会日時, 理由
  退会取り消し(E): 取消ID, 退会ID(FK), 取消日時
```

**登録日時・更新日時の一律付与は思考停止。** リソースには原則不要。イベントはStep 3により既に1つの日時属性のみ。

### Step 5: リソースの区分とサブタイプ

業務上の扱いが異なる場合、区分とサブタイプで表現する:

```
社員(R): 社員ID, 氏名, 社員区分(CURRENT/RETIRED)
  ├─ 現役社員: 基本給, 部門ID, ...
  └─ 退職社員: 退職日, 退職理由, ...(個人情報は消去)
```

実装パターンの選択基準:

| パターン | 条件 |
|----------|------|
| シングルテーブル継承 | 横断検索が多い、属性差が少ない |
| 具象テーブル継承 | 横断検索がほぼない、属性差が大きい |
| クラステーブル継承 | 横断検索あり、属性差が大きい |

**削除フラグは使わない。** 削除が必要なら区分テーブルやイベント抽出で対応する。

### リレーションシップの設計

#### リソース間: 交差エンティティで非依存にする

```
NG(非依存リレーションシップ):
  社員(R): 社員ID, 氏名, 部門ID(FK, Nullable)
  → 新入社員は部門ID=NULL、配属時にUPDATE必須

OK(交差エンティティ):
  社員(R): 社員ID, 氏名
  部門(R): 部門ID, 部門名
  所属(交差): 所属ID, 社員ID(FK), 部門ID(FK), 配属日時
  → INSERT ONLYでUPDATEなし
```

#### イベント間: 交差エンティティで分離する

```
NG:
  注文(E): 注文ID, 請求ID(FK, Nullable)
  → 注文時は請求ID=NULL、請求時にUPDATE必須

OK:
  注文(E): 注文ID, 注文日時
  請求(E): 請求ID, 請求日時
  請求明細(交差): 請求明細ID, 請求ID(FK), 注文ID(FK)
  → INSERT ONLYでUPDATEなし
```

#### 交差エンティティと履歴の分離

「現在の状態」と「過去の履歴」は分離する:

```
所属(R, 現在の状態): 所属ID, 社員ID(FK), 部門ID(FK)
配属(E, 履歴): 配属ID, 社員ID(FK), 部門ID(FK), 配属日時
```

### 履歴と世代管理

#### 過去データの履歴管理

```
非推奨(適用開始日/終了日方式):
  商品価格: 商品ID, 価格, 適用開始日, 適用終了日
  → すべてのクエリにBETWEEN条件が必須

推奨(シングル世代テーブルパターン):
  商品(R, 現在): 商品ID, 現在価格
  商品価格履歴(E): 商品ID, 価格, 開始日時
  → 現在はシンプルに参照、過去のみ履歴管理
```

#### 未来データの世代管理

複雑な世代管理が必要な場合はバージョンタグ付けパターンを使う:

```
商品(R): 商品ID, 商品名, バージョン
商品価格(R): 商品ID, バージョン, 価格, 有効フラグ(CURRENT/DRAFT/ARCHIVED)
```

### エンティティの検証(3大要素)

設計時に関係者間で合意すべき3点:
1. **単一性(Oneness)**: 何が1つのものか？(全6回の連載記事は1つ？6つ？)
2. **同一性(Sameness)**: 2つが同じと判断する条件は？(内容書き換え後、同じ記事？別の記事？)
3. **カテゴリ(Category)**: 分類の範囲は？(クライアント入稿のみ？ライター依頼も含む？)

### 設計原則まとめ

| 観点 | ルール |
|------|--------|
| UPDATE最小化 | イベント分割、交差エンティティで非依存化 |
| イベントの日時属性 | 1エンティティにつき1つのみ |
| リソースの日時属性 | 原則不要。必要なら隠れたイベントを抽出 |
| リレーション | NullableなFKは交差エンティティに分離 |
| 登録/更新日時 | 一律付与しない |
| 削除 | フラグより区分・イベント抽出を優先 |
| 履歴 | 現在の状態と過去の履歴を分離 |
